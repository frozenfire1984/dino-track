# Проект: браузерный 2D endless runner

Это личный учебный pet-проект: небольшая браузерная 2D-игра в жанре endless runner на Phaser + TypeScript + Vite.

Первоначальная идея вдохновлена Chrome Dino, но постепенно игра должна превратиться в самостоятельную дружелюбную игру для моей 7-летней дочери.

## Главный принцип разработки

Это НЕ vibe coding.

Основной разработчик — я. Обычный игровой и прикладной код я хочу писать руками, потому что одна из целей проекта — изучение Phaser, TypeScript и основ разработки игр.

Не реализуй самостоятельно фичи, не переписывай целые файлы и не генерируй большие куски кода без моей прямой просьбы.

По умолчанию сначала объясняй проблему и предлагай направление решения, после чего я сам вношу изменения.

Исключением могут быть сложные изолированные алгоритмы, нетривиальная математика/геометрия, особенно неприятная TypeScript-типизация и другие технические задачи, образовательная ценность самостоятельного написания которых невелика. Такие задачи я могу явно поручить ИИ.

## Первая версия игры

Первая версия должна быть максимально простой.

Персонаж находится примерно в одной горизонтальной позиции, а мир и препятствия движутся справа налево, создавая ощущение бега.

Игрок нажимает/тапает, чтобы перепрыгивать препятствия.

На старте нужны только:

- один персонаж — динозаврик;
- один вид препятствия — кактус;
- движение мира;
- прыжок;
- столкновение;
- Game Over;
- перезапуск.

Затем постепенно могут появиться счёт/дистанция и плавное увеличение скорости с разумным ограничением сложности.

## Возможное развитие геймплея

Это направления развития, а НЕ требования к текущей архитектуре:

- разные виды и размеры препятствий;
- летающие препятствия;
- бонусы;
- дополнительные очки;
- временная неуязвимость;
- выбор персонажа;
- динозаврик, котик, зайчик и другие персонажи;
- разные анимационные состояния персонажей;
- смена дня и ночи;
- разные окружения и биомы;
- возможное разделение игры на уровни.

Игра предназначена в том числе для маленького ребёнка, поэтому сложность должна увеличиваться контролируемо, а не становиться бесконечной и нечеловеческой.

## Инженерное развитие

Первоначальный стек:

Phaser + TypeScript + Vite.

На начальном этапе Vue и backend не нужны.

Позже вокруг Phaser может появиться Vue-приложение с экранами игры, выбора персонажа, результатов, статистики, настроек и т. д.

Ещё позже может появиться backend. В качестве возможных вариантов рассматриваются Laravel и NestJS, но решение пока не принято.

В дальнейшем в проект также может быть добавлен Docker, если для него появится практический или учебный смысл.

Не нужно заранее проектировать архитектуру под эти будущие технологии.

## Визуальная часть

Визуальная часть — отдельная линия развития проекта и не является для меня учебной задачей.

Я не собираюсь изучать рисование, Photoshop или pixel art в рамках этого проекта.

Персонажи, игровые объекты, фоны и другие визуальные ассеты могут:

- генерироваться с помощью ИИ;
- браться из подходящих лицензированных game asset packs;
- постепенно заменяться и улучшаться по мере развития игры.

На раннем этапе допустимы очень простые временные ассеты.

Позже персонажам могут понадобиться наборы кадров/спрайтов для разных состояний, например:

- idle;
- run;
- jump;
- hit;
- другие состояния по мере необходимости.

Моя задача как разработчика — научиться загружать эти ассеты в Phaser, создавать из них анимации и управлять состояниями персонажа, а не рисовать сами изображения.

При работе с готовыми сторонними ассетами необходимо учитывать их лицензии.

## Три линии развития проекта

У проекта есть три относительно независимые линии.

1. Геймплейная/Phaser — игровые механики, физика, препятствия, бонусы, персонажи, анимации, уровни.

2. Инженерная — TypeScript, позднее Vue, backend (Laravel или NestJS), база данных и, возможно, Docker.

3. Визуальная — постепенное улучшение персонажей, препятствий, окружения и общего художественного стиля с помощью готовых ассетов или генеративных инструментов.

Первые две линии являются образовательными. Третья — нет.

## Главное архитектурное правило

Не проектируй сегодняшнюю архитектуру вокруг гипотетических будущих возможностей.

Будущие идеи задают направление развития, но новые абстракции должны появляться тогда, когда для них появляется реальная необходимость.

При ревью ориентируйся примерно на следующий порядок приоритетов:

понимание → корректность → простота → поддерживаемость → расширяемость.

Цель проекта — не только получить готовую игру.

Главная образовательная цель — чтобы я понимал код и писал его сам.
